# 기능 개발 파이프라인

역할을 나눠 서로 검증한다. 핵심은 **만든 쪽과 채점하는 쪽의 분리**다.
테스터는 구현 과정을 보지 않은 새 맥락에서 완료 기준만 보고 검증한다.

```
요청 ─▶ ① PM: 명세 ─▶ [사용자 승인] ─▶ ② 개발 ─▶ ③ 테스터 ─┬─ 통과 ─▶ ④ PR·CI ─▶ ⑤ 보고 ─▶ 사용자(병합)
                                          ▲                │
                                          └── 결함 (최대 3회) ┘
```

| 단계 | 담당 | 입력 | 산출물 | 수정 가능 경로 |
|---|---|---|---|---|
| ① 명세 | `pm` 에이전트 | 사용자 요청, 저장소 | `docs/specs/<기능>.md` | `docs/specs/` 만 (훅으로 강제) |
| ② 구현 | 메인 세션 | 승인된 명세 | `feature/<기능>` 브랜치 커밋 | 제한 없음 |
| ③ 검증 | `tester` 에이전트 | 명세의 완료 기준, 브랜치 | `tests/acceptance/test_<기능>.py`, `docs/test-reports/<기능>-<회차>.md` | `tests/`, `docs/test-reports/` 만 (훅으로 강제) |
| ④ PR | 메인 세션 | 테스터 통과 | GitHub PR, CI 결과 | — |
| ⑤ 보고 | `reporter` 에이전트 | 명세·커밋·테스트 보고서·CI | `docs/reports/<기능>.md` | `docs/reports/` 만 (훅으로 강제) |

## 메인 세션(오케스트레이터) 진행 규칙

1. **명세:** `pm` 에이전트를 호출해 명세를 받는다. 명세의 "확인 필요" 항목과 범위를 사용자에게 보여 주고 **승인을 받은 뒤** 구현한다. 사용자가 "승인 없이 진행"이라고 하면 건너뛴다.
2. **구현:** `feature/<기능>` 브랜치를 만들고 명세대로 구현한다. 자체 단위 테스트를 쓰고 `pytest` 를 통과시킨 뒤 **커밋한다** (테스터는 커밋된 코드를 본다).
3. **검증:** `tester` 에이전트에게 넘기는 메시지에는 **명세 파일 경로와 브랜치 이름만** 준다. 구현 설명, 어려웠던 점, 테스트 힌트를 주지 않는다 — 독립성이 깨진다.
4. **수정 루프:** 테스터가 결함을 보고하면 고치고 커밋한 뒤 다시 검증받는다. **3회차에도 실패하면 멈추고** 남은 결함과 판단이 필요한 점을 사용자에게 보고한다.
5. **PR:** 통과하면 브랜치를 푸시하고 PR 을 연다. CI 가 통과할 때까지 확인한다. 병합하지 않는다.
6. **보고:** `reporter` 에이전트가 보고서를 쓰면, 그 요약과 PR 링크를 사용자에게 전한다. 에이전트의 출력은 사용자에게 보이지 않으므로 메인 세션이 전달한다.

## 관문 (다음 단계로 가는 조건)

| 관문 | 조건 |
|---|---|
| 명세 → 구현 | 완료 기준이 검증 가능한 문장으로 쓰여 있고, 사용자가 승인 |
| 구현 → 검증 | 브랜치에 커밋됨, 전체 `pytest` 통과 |
| 검증 → PR | 테스터 판정 "통과", 완료 기준 전부 충족 |
| PR → 보고 | CI 녹색 |

## 산출물 형식

- 명세: `docs/specs/_template.md` 를 따른다.
- 테스트 보고서: 판정(통과/불통과), 완료 기준별 결과 표, 결함 목록(재현 방법·기대·실제·심각도).
- 최종 보고서: 무엇을 왜, 변경 요약, 검증 결과, 남은 위험, 사용자가 할 일(PR 병합 등).
